# Release, Store Submission and Ongoing Operations

## 1. Environment strategy

`dev` debug for engineers with deterministic fixtures; `beta` release-mode with no fake data on fresh installs and authorized tester distribution; `production` signed retail build. Flavor/config selection must not introduce a hidden demo mode into retail. Version via semantic product release (`1.0.0`) plus monotonically increasing platform build numbers, managed in CI/release script. No server infrastructure in v1; no need to deploy cloud functions or create user accounts.

Established owner-approved identity: **Loop**, Android application ID and iOS Bundle Identifier **`com.jameskierdoliguez.loop`** in every app configuration. Initial engineering version is `0.1.0+1`; do not treat that debug shell as a release candidate. Never change the identifiers without approval. Verify their availability/ownership in both stores before production publication; no availability check, signing account or store connection has occurred. See [native foundation](NATIVE_FOUNDATION.md) for checked metadata/runtime pins and [M03](verification/M03.md) for actual debug/simulator builds. Deterministic design fixtures live in the separate preview/test harness; product debug startup also begins empty.

## 2. Pre-production readiness checklist

- Brand uniqueness/trademark/availability review for **Loop** (name is generic; do not assert exclusivity) including Apple/Play listing conflicts, domain and icon similarity.
- App package/bundle IDs under owner's controlled reverse domain; store identities/teams verified; secure and reviewed signing.
- Privacy Policy public reachable HTTPS page, in-app accessible link, support/contact email, Terms if appropriate; reflect actual SDK capabilities/data flow. Owner/legal review.
- Permission purpose strings: microphone, camera, photo picker, notifications appropriate, accurate and localized; ask only on usage.
- Google Play declaration: data safety, content rating, app access (no login), target SDK/current policy, screenshot dimensions, category, ads/no ads, financial claims none, background behavior disclosures.
- Apple: App Privacy, required API reasons/privacy manifests for included SDKs, App Review guideline checks, iOS deployment target, microphone/photo usage descriptions, export compliance as applicable, screenshots, review notes, support URL.
- Subscription/IAP metadata not needed in free v1. No in-app subscription screens with inert purchases.
- Store copy differentiates practice journaling from scientifically validated proficiency testing. Don't promise guaranteed skill gains or AI coaching.

## 3. Release pipeline

1. Freeze accepted M13 candidate, publish changelog, tag reviewed commit after owner sign-off.
2. Audit dependencies/licenses, secret scan, platform permission manifests, version numbers, debug symbols, release build size and performance.
3. Run CI all gates, M14 device test matrix and test explicit fresh/upgrade/migrate/export/restore on iOS and Android.
4. Generate signed AAB/APK for internal track and iOS signed IPA/TestFlight build through approved signing. Upload only with explicit owner authorization.
5. Run limited beta rollout; maintain issue tracker and fix critical defects. Reissue builds as necessary; don't carry P0/P1 into production.
6. Prepare product-page media and locale-copy, legal URLs, privacy disclosures, support docs, **test internal app install**.
7. Use Play staged percentage rollout and App Store phased release where supported, after explicit owner authorization; observe feedback, support issues and crash indicators under privacy-consent constraints.
8. Record actual approval/rejection decisions, distribution URLs and version checksums in `docs/verification/M15.md`. A built APK is not proof of published stores.

## 4. App store listing assets

- 1024px product icon master source file, adaptive Android icon with proper safe zones, Apple icon variants generated by supported tooling.
- Screenshot sets for supported device sizes: Today / Practice / Then-vs-Now / Progress / Library, using synthetic demo data **for marketing previews** labeled appropriately and not claiming real user results.
- Localized app description and keywords, preview copy, age rating rationale, changelog, onboarding FAQ, support/legal URLs, feedback route.
- Marketing landing page is optional but if built: Next.js TypeScript, Tailwind and shadcn may be used; browser/headless tests and Web Design Guidelines apply. It cannot gate the native app release except for required policy/support URLs.

## 5. Ongoing operation without backend

- Store support inbox/process for incoming bug reports, privacy/data recovery requests and version compatibility.
- Keep readable, source-controlled archive format specification and tested restore paths for prior archive versions.
- Scheduled dependency vulnerability checks and quarterly platform SDK policy review. Maintain App Store/Play policy changes and OS release behavior.
- Check user-feedback trends in optional beta survey rather than opaque individual tracking. Never collect personal recordings for debugging unless user explicitly shares a sanitized sample.
- Release support priorities: data recovery and permission regressions first, visual polish second. Maintain incident runbook: acknowledge, scope affected versions, stop rollout, publish workaround, patch, test import/migration, publish notes.
- Document no guaranteed ability to restore unexported data on a lost/uninstalled local-only app.

## 6. Rollback and forward compatibility

Application releases with schema migrations can be difficult to downgrade; build forward-fix and export recovery plan. Preserve old exports, never silently drop columns/data. For a dangerous update, pause distribution/rollout and ship patched version with compatibility; assess platform limitations of rollback. Restore rehearsals on previous and new versions required before major schema change. Maintain safe-mode diagnostic and export where possible.

## 7. Human release approvals

Owner must approve: trademark/brand, privacy and support language, signing and store accounts, optional subscription decisions, third-party analytics/crash services, externally indexed repository Graphify connection, release candidate, App Store/Google Play submission, and ongoing release cadence. Codex must stop before executing approval-gated actions, but can finish all permitted offline preparation.
